# #activities（課外經歷）內容架構規劃

## Context

`#activities`（課外經歷）目前分「社團／競賽／志工/服務學習」三個子群組，各只有 1 筆佔位範例，且**三者欄位結構完全不統一**：社團有「名稱＋角色」兩欄位，競賽有「名稱＋描述（成果／參與內容混在一起）」兩欄位，志工/服務學習則完全沒拆欄位（整筆只是一句話）。對應的 `_activities.scss` 仍是空檔案（1 行註解），從未像 `#skills`／`#portfolio` 一樣被認真規劃過。

依專案已確立的「設計新區塊固定流程」（見 `CLAUDE.md`），這輪先做內容架構規劃、只出規格文件，不動程式碼；使用者確認文件後才會另開一輪請求落地實作。

已確認方向（AskUserQuestion）：
1. **三個子群組統一成同一套必要欄位**（名稱/期間/角色/內容/成果），不像 `#skills` 語言類那樣刻意跟技術/工具不同調——因為社團/競賽/志工本質上都是「經歷紀錄」，沒有 `#skills` 語言類那種「有無外部檢定」的本質差異。
2. **這次一併規劃 `#skills`／`#activities` 的交叉引用欄位**（目前 `#skills` 的「用於 N 個作品」只連結 `#portfolio`，完全沒有「這個技能是透過某社團/競賽習得」的設計）。
3. 使用者判斷這個區塊**中高規模**（社團/競賽/志工合計會有不少真實資料），並主動要求提案「課外活動還能新增哪些資訊」——因此這份規格文件的補充資訊清單比照 `#portfolio` 當初的詳盡程度、更具創意地展開。

## 現況盤點

- `src/pages/index.html` 第 662–701 行：`#activities` 三個子群組，各僅 1 筆佔位。社團＝`activities__club-name`＋`-club-role`；競賽＝`activities__competition-name`＋`-competition-desc`（成果與參與內容混寫在同一欄）；志工＝`activities__volunteer`（單一 `<li>`，未拆 `<article>`／子欄位）。三者皆無時間欄位、無連結欄位、無交叉引用、無穩定 id。
- 第 236–244 行 `#resume`「校園經歷（精簡版）」：`resume__campus-list`／`-campus`，同樣扁平（單句、無拆欄位），HTML 註解（第 122–129、662–663 行）已明確定調：**`resume__campus` 是精簡重點，`#activities` 是完整版，兩者是同一份資料的詳略版本，刻意設計成「互相對應但不重複打字內容」**——這個治理邏輯跟 `#portfolio` spec 文件裡「`#resume` 專案經歷與 `#portfolio` 視為同一份清單詳略版本」完全同構，這次直接沿用同一套判斷，不用重新討論。
- `#skills` 的 `.skills__evidence`「用於 N 個作品」目前措辭與連結對象都**只指向 `#portfolio`**，完全沒有涉及 `#activities`；`docs/superpowers/specs/2026-07-23-skills-redesign-design.md` 當初的設計範圍也明講只涵蓋 portfolio/resume。
- `_activities.scss` 確認為空檔案。`FuturePlan.md` 全文檢查過，沒有任何跟課外經歷/社團/競賽/志工相關的既有規劃紀錄，這是全新主題。
- Nav／DOM 順序：`#activities` 位於「作品集」與「案例故事」之間，前後不相鄰於任何已規劃過的區塊。

## 內容架構：必要資訊 vs. 補充資訊

### 必要資訊（社團／競賽／志工三個子群組統一套用）

| 欄位 | 說明 | 現況 |
|---|---|---|
| 名稱 | 社團名稱／競賽名稱／志工服務名稱或單位 | 三者皆有，但志工目前混寫在單句裡未獨立 |
| 期間／時間 | 例如「2024.09–2025.06」或單一日期（志工單次服務可能只需單一日期） | **三者皆無**，這是目前最大的缺口 |
| 角色／身份 | 擔任幹部／組員／參賽者／志工身份等 | 社團已有；競賽、志工目前沒有獨立欄位 |
| 具體參與內容 | 做了什麼、怎麼參與的，跟「成果」分開寫，避免像現在競賽「成果／參與內容混在一起」看不清楚 | 社團/競賽現況都缺這個獨立欄位；志工完全沒有 |
| 成果與收穫 | 學到什麼、具體成果（量化更好），呼應全站「陳姐不信自誇形容詞」的誠實感原則 | 競賽現況混寫在描述裡；社團、志工皆無 |

### 補充資訊

#### Tier 1：中高規模下，現在就該把欄位／命名定案

| 欄位 | 說明 |
|---|---|
| 佐證連結／證書 | 活動照片、得獎證書、新聞報導、社團官方網站等連結——比照 `#portfolio` 的 `link-list` 概念，讓經歷有外部可查證的依據 |
| 名次／成果徽章 | 競賽名次（例如「全國賽 季軍」）視覺上獨立成一個小徽章元素，不要塞在敘述文字裡，方便快速掃描 |
| **`#skills`／`#activities` 交叉引用** | 呼應「經歷 → 技能」反向連結：每筆活動經歷可以標記「透過此經歷培養的技能」，`#skills` 那邊則需要新增對應的展開區塊。**設計重點**：目前 `#skills` 的「用於 N 個作品」語意是「應用場景」（果），而「透過某社團習得」語意是「養成來源」（因），兩者性質不同，建議在 `#skills` 卡片內拆成**兩個獨立的展開區塊**（「用於 N 個作品」連 `#portfolio`；「透過 N 個經歷習得」連 `#activities`），而不是混在同一個「用於 N 個作品」欄位裡，避免語意混淆 |
| 軟實力／可轉移技能標籤 | 例如「溝通」「領導」「時間管理」「危機處理」，用類似 `#skills`／`#portfolio` 的 `#` chip 標籤呈現，讓 HR 能快速掃描「這段經歷展現了什麼能力」——履歷/課外活動描述中常見但目前全站沒有這個呈現角度 |
| 精選／亮點標記 | 呼應 `#portfolio` 已規劃過的做法，讓少數最想被看到的經歷（例如擔任過社長、拿過全國名次）排在前面或視覺上更突出 |
| 服務對象／受益對象 | 志工類特有欄位，例如「服務對象：偏鄉兒童」「服務對象：獨居長者」，是志工經歷很難省略的關鍵資訊 |
| 時數／次數量化 | 志工常見的服務時數認證（例如「累計 40 小時」），或社團活動參與次數，量化呈現呼應 `#skills` 年資尺標「用數字說話」的誠實感原則 |
| 組織規模／層級 | 社團人數規模、競賽層級（校內／全國／國際），幫讀者判斷經歷的份量與含金量 |

#### Tier 2：真的量很大或有實際素材時再加

| 欄位 | 說明 |
|---|---|
| 時間軸視覺整合 | 比照 `#resume` 教育/實習經歷已用過的時間軸視覺（左側細線＋圓點），若同一社團內有多年參與紀錄，可以用時間軸呈現角色演進 |
| 角色演進／晉升軌跡 | 同一社團內逐年晉升的紀錄（例如組員 → 副組長 → 組長），現階段用文字描述即可，不需要獨立資料結構 |
| 合作對象／團隊夥伴 | 跨系所/跨校合作、與外部單位協辦等資訊 |

## Governance 決策

1. **`#resume` 校園經歷精簡版與 `#activities` 視為同一份清單的詳略版本**：沿用程式碼中已經明確寫下的既有決策（第 122–129、662–663 行），不重新討論；日後新增/修改任一筆經歷，兩處的名稱、期間、角色要保持一致。
2. **三個子群組統一必要欄位結構**：不再是「社團兩欄、競賽兩欄（且混寫）、志工零欄」的零散狀態，一致改成「名稱／期間／角色／內容／成果」五欄。
3. **`#skills`↔`#activities` 交叉引用要建立穩定 id 基礎建設**：比照 `#portfolio` 已經做過的 `id="portfolio-{slug}"` 模式，`#activities` 每筆經歷也要有穩定錨點 id（例如 `id="activities-{slug}"`），供 `#skills` 未來的「透過 N 個經歷習得」連結指向具體項目。
4. **`#skills` 措辭需要跟著調整**：「用於 N 個作品」與「透過 N 個經歷習得」是兩個語意不同、需要分開呈現的獨立展開區塊，不要合併成一個欄位硬塞兩種資訊。

## 如何展現特色

- 延續全站「誠實感優先、避免灌水」的內容設計原則：成果與收穫欄位鼓勵量化（時數、名次、具體數字），跟 `#skills` 65 年尺標、`#portfolio` NDA 誠實標註是同一套價值觀的延伸。
- 軟實力標籤沿用 `#` + Space Mono chip 的全站標籤語彙（`about__tag`／`skills__name`／`portfolio__tech` 同一套視覺簽名），不另創新樣式。
- 名次徽章、精選標記走「安靜的差異化」（小徽章/排序），不要做成搶眼的貼紙式設計，維持跟 `#portfolio` NDA 標註、精選標記一致的克制調性。

## 實作前必須確認的技術選型清單

供使用者確認這份規格文件時一併回答，避免下一輪實作又要重新開一輪釐清：

1. **視覺呈現方式**：這次要維持貼版面的清單式呈現（跟 `#resume`／`#skills` 一致），還是也要像 `#portfolio` 一樣做成卡片集？
2. **是否需要篩選/分類 UI**：中高規模下是否需要像 `#portfolio` 一樣做篩選器（例如依「社團/競賽/志工」或「年級」篩選），還是三個子群組分開陳列已經足夠？
3. **`#skills` 交叉引用要不要這輪一起落地**：這份文件已經把交叉引用的欄位命名定案，但實際去修改 `#skills` 的 HTML/SCSS（拆出「透過 N 個經歷習得」展開區塊）是否放在 `#activities` 這輪一起做，還是分開兩輪？
4. **軟實力標籤是否要建立獨立分類系統**（例如像 `#portfolio` 的作品類型一樣建立一套標準化的標籤詞彙表），還是先讓使用者自由填寫、不強制分類？

## 本次分析範疇

這份文件只是內容架構規劃，**尚未動任何程式碼**——`_activities.scss` 仍是空的，`index.html` 的 `#activities` 結構也還是原本的最小佔位版本，`#skills` 也還沒新增交叉引用區塊。是否要接著進入實作，需要使用者確認這份規劃（含上方技術選型清單）後才進行。
