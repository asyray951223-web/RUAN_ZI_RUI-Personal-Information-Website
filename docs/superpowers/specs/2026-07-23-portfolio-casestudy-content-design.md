# #portfolio（作品集）＋ #casestudy（案例故事）內容架構規劃

## Context

`#portfolio` 與 `#casestudy` 從網站五大核心區塊／加分區塊建立以來，一直維持最初的最小佔位結構：各只有 1 筆佔位範例，對應的 `_portfolio.scss`／`_casestudy.scss` 都還是空檔案（只有一行註解），從未像 `#skills`（見 `2026-07-23-skills-redesign-design.md`）一樣被認真盤點過內容欄位。

使用者要求比照 `#skills` 當初的 brainstorming 流程，先規劃「作品集」需要哪些必要資訊、哪些是可補充資訊，盡可能詳細，並確認了三個方向：

1. **這次只出內容欄位規劃的規格文件，不動程式碼**——比照 `#skills` 的兩階段模式：先出規格文件，使用者確認後才另開一輪請求落地實作（改 `index.html` 結構＋補 `_portfolio.scss`/`_casestudy.scss` 樣式）。
2. `#resume`「專案經歷」與 `#portfolio` **視為同一份專案清單的詳略版本**（resume 是精簡摘要、portfolio 是完整版），兩邊的核心事實（名稱、角色、技術標籤）應保持一致，不應該各自獨立到可以是不同的作品。
3. 使用者明確表示**長期會有大量作品，作品集是本網站的重點內容之一**——這代表「分類篩選」「精選代表作標記」「穩定錨點 ID」這類支援規模化的資訊架構決策，即使視覺／篩選 UI 之後才做，**欄位命名與必要性現在就該定案**，避免以後作品變多時要回頭幫每筆舊資料補欄位。

## 現況盤點

- `src/pages/index.html` 第 535–566 行 `#portfolio`：1 筆 `.portfolio__item` 佔位，欄位＝封面圖（`portfolio__cover`）、類型（`portfolio__type`）、名稱（`portfolio__name`）、一句話摘要（`portfolio__summary`）、技術標籤（`portfolio__tech-list`/`-tech`）、角色（`portfolio__role`）、成果與收穫（`portfolio__outcome`）、連結清單（`portfolio__link-list`/`-link-item`/`-link`，目前只有「線上 Demo」「GitHub」兩個 `href="#"` 假連結）。
- 第 609–655 行 `#casestudy`：1 筆 `.casestudy__item`，5 段式敘事（背景／目標／過程／挑戰／成果與收穫）。HTML 註解明確定義「從 portfolio 挑 1-2 個最想深談的作品做深度版」，但**目前沒有任何程式碼層級的雙向連結**——沒有 id 對應、沒有錨點，兩者的關係純粹靠命名慣例與註解說明，資料要人工同步維護。
- 第 194–218 行 `#resume` 專案經歷：`resume__project-title`／`-desc`／`-role`／`-tags`／`-link`。HTML 註解已明講「命名對齊下方 `#portfolio` 的 role/tech-list/link-list，避免同一種資訊取兩套命名」。目前沒有時間欄位，連結是單一個（非清單）。
- 第 326–334 等處 `#skills` 的 `.skills__evidence-link`「用於 N 個作品」：目前是純文字佔位＋`href="#"` 假連結，**並未真正指向 `#portfolio`／`#casestudy` 的特定項目**——因為 `.portfolio__item` 目前沒有各自的 id，這條連結線是「預留但基礎設施未到位」的狀態。
- `_portfolio.scss`／`_casestudy.scss` 皆為空檔案，尚未有 layout／卡片化樣式，`.portfolio__list`/`.casestudy__list` 目前吃瀏覽器預設 `<ul>` 樣式。
- `FuturePlan.md`「規劃三」：已確認暫不把作品集拆成獨立分頁，維持單頁錨點架構；但記錄了未來展望「首頁精選幾件代表作＋連結到完整作品集頁」——這呼應「精選代表作」欄位即使不拆頁，也能先用「標記＋排序」在同一頁面內做出類似效果，等以後真的需要拆頁時，也能直接沿用同一套「精選」判斷。
- Nav 中「作品集」與「案例故事」是兩個平行、獨立的錨點選單項目，並非主從關係，DOM 順序也不相鄰（`#portfolio` 之後接 `#activities`，再接 `#casestudy`）。

## 內容架構：必要資訊 vs. 補充資訊

### 必要資訊（每筆作品都要有）

| 欄位 | 說明 | 現況 |
|---|---|---|
| 封面圖／預覽圖 | 視覺入口，第一眼判斷內容類型 | 已有 `portfolio__cover` |
| 作品名稱 | | 已有 `portfolio__name` |
| 一句話摘要 | 電梯簡報式摘要，供快速掃描 | 已有 `portfolio__summary` |
| 作品類型／性質 | 課程作業／自主練習／專題競賽／實習成果／Side Project——回答「這是什麼場合做的」 | 已有 `portfolio__type`；長期作品變多後，這也會是主要篩選軸之一 |
| 技術／工具標籤 | | 已有 `portfolio__tech-list` |
| 角色與分工 | 獨立完成或團隊分工，具體負責什麼——團隊專案中判斷個人貢獻度的關鍵資訊 | 已有 `portfolio__role` |
| 具體成果與收穫 | 學到什麼、有沒有具體成果，鼓勵量化（比照 `#skills` 規劃時「陳姐不信自誇形容詞」的原則，量化數字比「學到很多」更有說服力） | 已有 `portfolio__outcome` |
| 對外連結，或明確的不可公開原因 | Demo／GitHub；若因保密協議無法公開，需寫明原因而非留空或死連結，避免讀者誤以為忘記放連結 | 連結已有；「無法公開」的替代說明目前沒有欄位——見下方 NDA 標註，已提升為必要資訊 |
| 時間／完成期間 | 例如「2025.03–2025.06」 | **目前沒有**，建議新增：用於排序（新到舊）、判斷技術新舊、之後篩選「近一年作品」 |
| 穩定錨點 ID／slug | 每個 `.portfolio__item` 專屬、不隨內容修改而變動的識別碼 | **目前沒有**，屬於基礎建設而非顯示內容，但因為長期作品量大、且 `#skills`／`#resume`／`#casestudy` 都需要指向具體作品，現在就該定案命名規則（例如 `id="portfolio-{slug}"`），避免以後補標籤要動到既有的跨區塊連結 |

### 補充資訊

#### Tier 1：因為長期會有大量作品，建議現在就把欄位／命名定案（篩選 UI 可以晚點做）

| 欄位 | 說明 |
|---|---|
| 分類篩選標籤 | 獨立於技術標籤的另一個篩選軸，例如「前端／後端／資料／App／設計」這種「技術領域分類」——回答「這是哪個技術領域的」，跟「作品類型」（回答「這是什麼場合做的」）是兩個不同維度，不應該合併成同一組標籤，否則之後做篩選 UI 時兩種語意會互相干擾 |
| 精選／代表作標記 | 呼應 `FuturePlan.md`「首頁精選幾件代表作」的展望——即使不拆頁，也能用這個標記讓少數代表作排在列表最前面或視覺上更突出，其餘作品仍完整收錄但不搶版面。長期作品一多，這是避免頁面變成「大家都同等份量、看不出重點」的關鍵欄位 |
| 案例故事雙向連結 | `.portfolio__item` 若有對應的 `#casestudy` 深度版，要有「閱讀完整案例 →」連結；反過來 `#casestudy` 也該標明「這是哪個作品的深度版」並可連回 `#portfolio` 對應項目。目前兩者關係只靠人工註解維繫，沒有任何程式碼層級的關聯 |
| 保密／無法公開標註（NDA） | 實習或公司內部專案常見「不能放代碼／畫面」的情況，需要明確欄位讓讀者知道「不是忘記放連結，而是不能公開」（因為與必要資訊的「對外連結」直接相關，實作時建議兩者合併設計，而非兩個獨立欄位） |

#### Tier 2：作品量真的變大、或有實際素材時再加

| 欄位 | 說明 |
|---|---|
| 更新日期 | side project 持續維護時標註「最近更新：2026-XX」 |
| 團隊規模 | 補充「角色與分工」的量化背景，例如「3 人小組，負責前端」 |
| 結構化量化指標 | 目前 `portfolio__outcome` 是自由文字；未來若累積夠多可量化數據（GitHub star、使用者數、效能提升 %），可考慮拆成獨立的「指標小卡」視覺元件；現階段文字敘述已足夠，不需要為了少數幾筆資料就先做結構化欄位 |
| 影音／動圖 Demo | GIF 或影片內嵌（需自架，不用外部 CDN，符合本站慣例），適合互動性強的 UI 作品；現階段封面靜態圖已是可接受的最小可行版本 |

## Governance 決策

1. **`#resume` 專案經歷與 `#portfolio` 視為同一份專案清單的詳略版本**：日後新增／修改任一專案時，名稱、角色、技術標籤兩處要保持一致（僅描述長度、是否含成果細節不同），不應該出現「resume 說負責前端、portfolio 說負責全端」這種事實矛盾。
2. **錨點 ID／分類篩選軸／精選標記，現在就定案命名，不等以後**：因為使用者明確表示作品集是長期重點內容、量會變大，晚定案的代價（回頭幫每筆舊資料補欄位）比現在多花一點設計時間高。
3. **NDA／無法公開標註提升為必要資訊**：資訊管理／全端開發學生常見有實習專案不能公開，這個欄位缺席會讓讀者誤以為忘記放連結，影響專業印象；實作時建議與「對外連結」欄位合併處理（有連結顯示連結，沒有則顯示不可公開原因），而非兩個並存的獨立欄位。
4. **`#skills` 的「用於 N 個作品」與 `#portfolio`／`#casestudy` 的連結，等 `.portfolio__item` 有穩定 id 後才能真正指向具體項目**：這是三個區塊資料串接的關鍵前提，實作階段應優先處理。

## 如何展現特色（延續全站既有語彙，供實作參考）

- 新欄位沿用既有 BEM 命名慣例，不另創一套系統：例如時間欄位可比照 `resume` 的日期寫法（`2025.03–2025.06`）；分類標籤沿用 `portfolio__tech-list` 的標籤視覺語彙，但用不同的視覺區隔（例如顏色或位置）避免跟技術標籤混淆。
- 精選標記建議走「安靜的差異化」，例如一個小徽章或些微的排序/尺寸調整，而不是誇張的貼紙式設計，維持全站「誠實感、不灌水」的一貫調性（呼應 `#skills` 規劃時「陳姐不信自誇形容詞」的原則——精選標記是給讀者導覽用的訊號，不是自我宣傳）。
- NDA 標註建議用中性、專業的文字語氣呈現（例如「因保密協議無法公開原始碼，僅呈現流程與心得」），避免讀起來像抱歉或藉口。

## 建議的 HTML 欄位命名對照表（實作階段參考，這次不落地）

| 用途 | 建議命名 | 說明 |
|---|---|---|
| 穩定錨點 | `id="portfolio-{slug}"` 或 `data-portfolio-id` | 放在 `.portfolio__item` 或內層 `<article>` 上，供 `#skills` evidence link／`#casestudy` 反向連結使用 |
| 完成期間 | `.portfolio__date` | 比照 `resume` 專案經歷的日期寫法 |
| 分類篩選標籤 | `.portfolio__category-list` / `.portfolio__category` | 與現有 `.portfolio__tech-list` / `.portfolio__tech` 並列，語意上分開（分類 vs 技術） |
| 精選標記 | `.portfolio__featured`（modifier class 或徽章元素） | 加在 `.portfolio__item` 上作為 modifier，例如 `.portfolio__item--featured` |
| 案例故事連結 | `.portfolio__casestudy-link` | 只有存在對應 `#casestudy` 項目時才輸出這個元素 |
| 無法公開標註 | `.portfolio__nda-note`（與 `.portfolio__link-list` 二擇一顯示） | 有公開連結時顯示連結清單，沒有則顯示這個說明文字 |

## 本次分析範疇

這份文件只是內容架構規劃，**尚未動任何程式碼**——`_portfolio.scss`／`_casestudy.scss` 目前仍是空的，`index.html` 的 `#portfolio`／`#casestudy` 結構也還是原本的最小佔位版本。是否要接著進入實作（改 HTML 結構補上新欄位、幫 `.portfolio__item` 加穩定 id、串接 `#skills` evidence link，並補齊 SCSS 樣式），需要使用者確認這份規劃後才進行。
