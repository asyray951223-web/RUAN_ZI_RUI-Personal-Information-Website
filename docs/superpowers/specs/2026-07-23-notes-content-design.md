# #notes（學習筆記）內容架構規劃

## Context

`#notes` 目前只有 1 筆佔位（標題連結、摘要、日期），對應的 `_notes.scss` 完全空白（只有 1 行註解），是繼 `#casestudy` 之後另一個尚未認真規劃過內容架構的核心區塊。

依專案已確立的「設計新區塊固定流程」（`CLAUDE.md`），這輪先做內容架構規劃、只出規格文件，不動程式碼；使用者確認文件後才會另開一輪請求落地實作。

已用 AskUserQuestion 確認三個方向：
1. **筆記連結最終連到外部平台**（Medium／個人部落格／Notion 等），不是站內獨立頁面——這跟 `FuturePlan.md`「規劃三」當初記錄的「學習筆記未來可能需要列表頁＋各篇內文頁」的部落格式展望不同方向：這次確認全文維護在外部平台，本站只放摘要＋外部連結，不需要規劃站內詳情頁。
2. **「分類/類型」獨立成必要欄位**，比照 `portfolio__type` 的做法——目前佔位文字「課程筆記／技術學習／讀書心得」已經暗示這個分類概念，這次把它正式拆成欄位。
3. **規模預期中高量（部落格性質，會持續累積）**，跟 `#casestudy` 的「少量精選」明顯不同——這代表分類篩選、排序等擴充性欄位命名要現在就定案，即使篩選 UI 可以晚點做。

## 現況盤點

- `src/pages/index.html` 第 1086–1106 行：`#notes` 1 筆佔位，`notes__title`（`<a>` 連結，`href="#"` 佔位）＋ `notes__excerpt` ＋ `notes__date`，`<h2 class="section__title">` 尚未升級 eyebrow 樣式。沒有分類欄位、沒有外部平台標示、沒有穩定 id。
- `src/styles/pages/_notes.scss`：完全空白，只有 1 行註解，是全站唯一連基本樣式都沒有的核心區塊（`#casestudy` 至少還有這輪剛補的樣式）。
- `FuturePlan.md`「規劃三」第 137、143 行：曾記錄學習筆記跟作品集一樣，未來內容量大時可能需要「列表頁＋各篇獨立頁」的部落格式結構，並列入拆頁觸發條件；這次確認全文交給外部平台維護，站內詳情頁的展望不再適用，但拆頁展望本身（列表頁形式）仍可能適用於「筆記列表」本身變長的情境，這屬於既有規劃三的範疇，這次不重新處理。
- `src/data/*.json` + `src/build/`：resume/skills/portfolio/activities/casestudy 五區塊皆已納入 JSON+建置腳本範圍（見 `claude_core_assistant.md` 第 39–46 筆），`#notes` 目前不在範圍內，技術選型清單會問是否納入。

## 內容架構：必要資訊 vs. 補充資訊

### 必要資訊（每篇筆記都要有）

| 欄位 | 說明 | 現況 |
|---|---|---|
| 筆記標題 | | 已有 `notes__title` |
| 分類/類型 | 例如：課程筆記／技術學習／讀書心得，比照 `portfolio__type` 獨立成欄位 | **目前沒有**，只是佔位文字裡的隱含概念，這次正式拆欄位 |
| 摘要 | | 已有 `notes__excerpt` |
| 日期 | | 已有 `notes__date` |
| 外部連結 | 連到全文實際維護的外部平台，取代目前的 `href="#"` 佔位 | 已有連結骨架，這次補上真正的目標語意（外部平台） |

### 補充資訊

#### Tier 1：中高規模預期下，現在就該定案命名（即使篩選 UI 晚點做）

| 欄位 | 說明 |
|---|---|
| 分類篩選 slug | 比照 `#portfolio`／`#activities` 已有的 `data-type` 命名模式，供未來篩選 UI 直接沿用，不需要屆時重新設計欄位 |
| 來源平台標示 | 例如「Medium」「個人部落格」「Notion」，讓讀者點擊前就知道會離開本站到哪個平台，管理閱讀體驗預期 |
| 精選/置頂標記 | 部落格性質內容量一多，讓少數代表作/重要筆記可以排在最前面或視覺上更突出，呼應 `#portfolio` 已規劃過的同類做法 |

#### Tier 2：量真的很大或有實際素材時再加

| 欄位 | 說明 |
|---|---|
| 細部標籤 | 除了大分類外更細的關鍵字標籤（例如「React」「資料庫」），供更精準篩選 |
| 閱讀時間/字數估計 | 部落格常見的輔助資訊，讓讀者評估要不要點進去看 |
| 系列/專題分組 | 多篇連載筆記歸類成同一個系列，現階段規模不需要 |

## Governance 決策

1. **筆記全文只在外部平台維護，本站不重複打字**：`#notes` 只放摘要＋外部連結，不規劃站內詳情頁，這跟 `#portfolio` 詳細頁（`project-1.html`，全文在站內）是不同的治理模式——因為使用者這次明確選擇「連到外部平台」而非「未來站內獨立頁」。
2. **分類欄位命名比照 `portfolio__type` 模式**（顯示文字 + `data-type` slug 兩層），為未來的分類篩選打好基礎，避免屆時要重新設計一套分類系統。
3. **外部連結要有明確的視覺提示**（例如箭頭符號），讓讀者在點擊前就知道會離開本站，不是站內錨點——這點列入下方技術選型清單讓使用者確認具體呈現方式。

## 如何展現特色

- 分類標籤沿用全站既有的 `#` + Space Mono chip 語彙，不另創新樣式。
- 外部連結沿用全站磚紅色 dashed underline 語彙，可以額外加一個小箭頭符號（↗）區分「站內錨點」與「站外連結」，呼應 `#portfolio` 詳細頁連結（→）與這次外部連結的語意差異。
- 這是全站第一個「內容全部交給外部平台維護」的區塊，展現特色的重點不在版面裝飾，而在於「清楚標示這是索引/導覽性質的清單」，管理讀者的預期。

## 實作前必須確認的技術選型清單

供使用者確認這份規格文件時一併回答：

1. **要不要納入 JSON + 建置腳本範圍**：`#notes` 中高規模預期（部落格性質，會持續累積），JSON 驅動的維護效益明顯，是否這輪就跟其他五區塊一樣納入？
2. **標題要不要一併升級成 eyebrow 樣式**：目前還是 `<h2 class="section__title">`，跟已升級的 `#portfolio`/`#activities`/`#casestudy` 不同步。
3. **這輪要不要就做分類篩選器 UI**：規模預期中高，可能值得這輪就仿照 `#portfolio` 做篩選器（需要 JS，沿用既有的 `src/scripts/filter.js`），還是先只定義好 `data-type` 分類命名，UI 留到筆記真的累積到一定數量再做？
4. **外部連結的視覺提示具體怎麼呈現**：只加箭頭符號（↗），還是要更明確的文字提示（例如「前往 Medium 閱讀全文」）？

## 本次分析範疇

這份文件只是內容架構規劃，尚未動任何程式碼——`_notes.scss` 仍是空的，`index.html` 的 `#notes` 結構也還是原本的最小佔位版本。是否要接著進入實作，需要使用者確認這份規劃（含上方技術選型清單）後才進行。
